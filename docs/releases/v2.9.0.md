## v2.9.0 🦕 Archaeopteryx — the Recovery app, and offline that actually works

Named for the lineage that outlived the extinction. This release is about IttyBitz outliving IttyBitz. **Cryptography is unchanged** — `src/lib/crypto.ts` was not touched, and every historical ciphertext back to v1.0 still decrypts.

### 🪶 A standalone Recovery app

**[`ittybitz.app/ittybitz-recovery.html`](https://ittybitz.app/ittybitz-recovery.html)** — one self-contained HTML file, 26 KB, that decrypts IttyBitz containers with no dependencies, no network, no build step and no installation. Download it, put it on a USB stick next to your encrypted files, and open it. It works on an air-gapped machine.

It exists because the real single point of failure here was never the cryptography — it was **availability**. Opening a 25-year-old backup used to require ittybitz.app to still resolve, GitHub Pages to still serve, and this build to still work. None of that is guaranteed for 25 years, and none of it is under your control. Keep this file beside your data and none of it has to be true.

Thanks to the user who asked for exactly this: *"just in case I were to die tomorrow and the project died with me."*

It decrypts only. That is deliberate — it halves the code you have to trust, and new long-term secrets should be created with the reviewed application.

**Why you can trust it, rather than just hope:** it reimplements container parsing and key derivation, which means it could silently drift from `crypto.ts`. So it does not get to be trusted on its own claims. The regression suite extracts the decrypt core straight out of the HTML and replays **all 32 historical fixtures** through it — v1.0 through v2.7.3, both wire formats, with and without key files, plus every rejection case. If the recovery file and `crypto.ts` ever disagree about a real ciphertext, CI fails. The suite is now **70 checks**.

Three more decisions worth knowing:

- **Its CSP enforces the "nothing is sent" promise** rather than asserting it: `default-src 'none'` blocks every network destination. Verified to block both cross-origin and same-origin requests.
- **It is byte-identical everywhere** — repo, website, and release asset — so the checksum published with it is verifiable no matter where you got the file. Verify with `shasum -a 256 ittybitz-recovery.html`.
- **The container format and key derivation are documented in full inside the file itself.** If the HTML ever fails to run, the data is still recoverable by anyone with an AES-256-GCM and PBKDF2 implementation. `view-source:` to read it.

### 📴 Offline finally works

**The PWA has never worked offline.** Reproduced from a clean install: after a full page load the cache held 7 entries — `/` and the icons — and **zero JavaScript or CSS**. Going offline rendered an unstyled, dead page; in an installed PWA, the manifest's background colour and nothing else.

The service worker precached only the static shell and left the chunks to be picked up "at runtime". That never happens on a first visit — the page's asset requests complete *before* the newly installed worker controls the page, so they bypass the fetch handler entirely and are never cached. Every release made it worse: activation deletes all old caches, then precaches only the shell again, so even a user who had chunks cached lost them on the next update.

The build now writes the real, content-hashed asset list into the service worker, fail-closed — the build fails if anything `index.html` needs is missing from it. It precaches all of `_next/static`, not just what the HTML references directly, which also covers the lazily-imported BIP-39 wordlist chunk; otherwise seed detection would still have broken offline.

Verified with the server genuinely stopped: 22 entries cached, the app renders fully, a v2.7.0-era ciphertext decrypts, the seed is detected, and the SeedQR generates with unchanged hashes.

This matters most for exactly the people this app is built for — anyone running it on an air-gapped machine.

### 🏷️ Clearer buttons

The two buttons at the top of the working card said only "File" and "Text", describing the input but not what would happen to it. They now name the action and follow the mode: **Encrypt a File / Encrypt Text** under Encrypt, **Decrypt a File / Decrypt Text** under Decrypt. With the object stated there, the action button is now simply **Encrypt** or **Decrypt**.
