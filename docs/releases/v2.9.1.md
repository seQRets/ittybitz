## v2.9.1 🦕 Archaeopteryx — nine defects from a full code review

A review pass over both the main app and the new Recovery app, fixing everything it found. **Cryptography is unchanged** — `src/lib/crypto.ts` has zero diff, and the Recovery file's decrypt core is byte-identical to v2.9.0, so all 32 historical ciphertexts still pass through both.

**If you use the Recovery tool, download it again** — this release replaces it. The README and `Recover/` links now point at this version.

### 🔑 The key-file toggle could be silently ignored

Turning on **Use key file** without selecting one let encryption proceed *password-only* while the UI said otherwise. Reproduced, then proven: the resulting ciphertext decrypted with no key file at all.

This was the serious one. It's a trap that springs at recovery time: you believe a key file protects your backup, you supply it when decrypting, it fails — because the key material differs — and you conclude the backup is corrupt. The button is now disabled in that state, and the operation refuses even if reached another way.

### Main app

- **First-time visitors no longer see "A new version is available — tap to reload."** The service worker announced an update on *first install*. It now only announces when it actually replaced a previous version. Verified on a clean install: 24 entries precached, worker controlling the page, no banner — and the app still renders fully with the server stopped.
- **A bad paste is no longer blamed on your password.** Stray characters in the encrypted text said *"password may be incorrect,"* so people retyped a correct password in vain. It now says *"The encrypted text is not valid Base64."*

### Recovery app

- **The password is cleared after every decrypt.** It was left sitting in the field — on a tool built for borrowed and air-gapped machines, exactly where that matters.
- **File mode now downloads.** A decrypted text file (`.txt`, `.md`, `.json`) was being displayed on screen instead, losing the filename with no way to save it. Mode now decides, matching the main app.
- **Errors are classified by type, not by keyword-matching messages.** A failed decryption is a `DOMException`; the tool's own format errors are plain `Error`s. Previously a file whose *name* contained "decrypt" could have a read failure reported as a wrong password. Proven three ways: wrong password → the generic message; a forged newer-version header → the tool's own "newer version" text intact; a validation message passes through untouched.
- A decrypted file that didn't end in `.ibitz` downloaded under its **own** name; it now gets a `decrypted-` prefix like the main app.
- Clicking an error message no longer blurs it (a reveal-toggle from a previous success lingered).
- Plaintext is best-effort zeroed after handoff, matching the main app. *This one is verified by inspection — it isn't observable from outside.*

### Verified

- Every behavioural fix exercised in the browser, including four full 1,000,000-iteration decryptions through the Recovery app.
